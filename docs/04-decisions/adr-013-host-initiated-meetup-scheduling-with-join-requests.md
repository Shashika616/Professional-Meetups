# [ADR-013](adr-013-host-initiated-meetup-scheduling-with-join-requests.md): Host-Initiated Meetup Scheduling with Join Requests, Replacing the Mock Matching Flow as the Real Phase 1 Discovery Mechanism

**Status:** Accepted — amends [Domain Model](../02-domain/domain-model.md)'s Match → Meetup relationship, [Trust Levels](../02-domain/trust-levels.md)'s per-intent trust floor, and retires the mock swipe-style Matches tab as a parallel/placeholder feature.

## Context

Shashika's proposed next feature (2026-08-17): any user can schedule a meetup — either "today" (intent, time, location, participant cap, created immediately) or "for later" (same fields plus a calendar date/time-slot picker) — and other users can request to join it. The host sees requesters' name and trust level and accepts or rejects each one; both sides get notified of the outcome.

This doesn't match the Meetup entity as currently defined. [Domain Model](../02-domain/domain-model.md) describes Meetup as downstream of a **Match** — a mutual pairing produced by a compatibility-matching engine (industry, interests, communities, location). That engine is real, nontrivial work (`<200ms`, NFR-001) and was never scoped for Phase 1 — [Roadmap](../06-roadmap/roadmap.md) lists "AI personal assistant / advanced matching" under Phase 3. The current `MatchesPage`/`MockMatchingService` in the frontend is a placeholder built to visualize the eventual matching-engine UX, not a real feature.

Three more things needed resolving before this could be planned, all raised and confirmed with Shashika:

1. **Trust gating**: Shashika's original phrasing ("all levels of trust users can schedule") textually conflicts with [Trust Levels](../02-domain/trust-levels.md)' Level 1b restriction ("cannot match or be matched") and [ADR-006](adr-006-progressive-linkedin-first-trust-onboarding.md)'s explicit statement that Level 2 is "the real floor for matching and messaging with strangers," not Level 1. Confirmed: gating stays per-intent (reusing `IntentType.requiredTrustLevel`, already built), not a blanket bypass.
2. **Safety Gate**: Shashika's description (schedule → accept/reject → done) omitted the checklist/live-location/check-in/post-meetup-feedback flow [Roadmap](../06-roadmap/roadmap.md) already commits to for Phase 1 and [Safety UX Flows](../05-ux/safety-ux-flows.md) already specifies step by step. Confirmed: the full Safety Gate is in scope for this build, not deferred.
3. **Relationship to the existing Matches tab**: confirmed this should be the *real*, production-grade feature — not a second parallel surface sitting next to the mock. The mock swipe-style matching UI is retired in favor of this.

## Decision

### 1. New host-initiated interaction model, alongside (not instead of) the eventual matching engine

Introduce a **Meetup** that a user creates directly (not derived from an algorithmic Match): intent, one of {today, scheduled}, date/time, location (lat/lng + address, via Google Places — see § 4), participant capacity, and status. A separate **Meetup Request** entity represents another user asking to join: requester, status (`pending`/`accepted`/`rejected`/`withdrawn`), timestamps. This supersedes the Match→Meetup pipeline as the Phase 1 mechanism for *how strangers actually end up meeting* — the compatibility-matching engine, if/when it's built in Phase 3, becomes a *discovery aid* that surfaces relevant open Meetups and suggests intents to a user, not a different creation path for Meetup records. [Domain Model](../02-domain/domain-model.md) is updated accordingly (§ 1 below is the doc change, this is the rationale).

### 2. Trust floor: per-intent, with the default raised from Level 1 to Level 2

`IntentType.requiredTrustLevel` currently gates only `rideShare`/`dating` at Level 4, defaulting everything else (`coffee`/`lunch`/`networking`/`mentorship`) to Level 1. Hosting or requesting to join a real-world meetup with a stranger is exactly the scenario [ADR-006](adr-006-progressive-linkedin-first-trust-onboarding.md) called "the real floor for matching and messaging with strangers" — Level 2, not Level 1. Changing the default:

| Intent | Old floor | New floor |
|---|---|---|
| coffee, lunch, networking, mentorship | 1 | **2** |
| rideShare, dating | 4 | 4 (unchanged) |

Level 1 (federated LinkedIn only) still unlocks browsing/profile-completion and *viewing* open meetups, per [ADR-006](adr-006-progressive-linkedin-first-trust-onboarding.md)'s low-friction-signup goal — it does not unlock hosting a meetup or sending/receiving a join request. This is a real behavior change from what's live today (Level 1a users currently see mock matches with no gate) — flagged here explicitly per the project's standing rule to surface safety-relevant defaults rather than let them drift in during a feature build.

### 3. Full Safety Gate is in scope for this build

Every accepted Meetup Request (or, for a 1:1 acceptance, every meetup that reaches its intended participant count) transitions the Meetup into the Safety Gate flow already specified in [Safety UX Flows](../05-ux/safety-ux-flows.md): safety checklist → optional live-location sharing → check-in timer → post-meetup confirmation from all confirmed participants. Not simplified for this slice. The "smart pickup recommendations" pattern from [Safety Features Catalog](../03-architecture/safety-features-catalog.md) (never suggest exact home locations, bias toward public establishments) applies to the location-picker step (§ 4).

### 4. Location: Mapbox, host picks an address with search/autocomplete or pin-drop

**Correction (2026-08-18), before any build started:** originally scoped as Google Maps + Places per Shashika's initial phrasing. Reconsidered after Shashika asked for a free alternative and confirmed to switch: **Mapbox** — `mapbox_maps_flutter` (official SDK, map render + pin) and the Mapbox Search Box API (address search/autocomplete, resolves to lat/lng) — cross-platform (Android + iOS), one vendor for both map and search instead of two. Chosen over self-hosted OpenStreetMap/Nominatim because Mapbox's place data is more actively maintained than raw OSM for Sri Lanka specifically (OSM's Sri Lanka coverage is road-navigation-focused with named-business/POI data comparatively weaker, per direct research at decision time — see chat record), which matters for a safety feature where correctly identifying a real public venue is the point; and because it's a single officially-maintained Flutter package rather than stitching a community map-tile package to a separate free-tier geocoder.

**Requires Shashika to create a Mapbox account and generate access tokens** — a public token (URL/bundle-restricted) for the SDK, scoped separately for Search — no GCP project or Google Cloud billing account needed for this piece specifically; confirm at signup whether Mapbox requires a card on file for its free tier (unconfirmed either way as of this writing, unlike Google's documented billing-required policy). Free tier at time of decision: 25,000 mobile map loads/month, 100,000 geocoding/search requests/month — comfortably covers an invite-only Colombo pilot ([ADR-005](adr-005-invite-only-company-based-closed-launch.md)). Logged in [Action Tracker](../00-project/action-tracker.md) as a prerequisite, same category as the Twilio/Resend/domain items (superseding the earlier Google Maps/Places entry there).

**Second correction (2026-08-18) — provisional testing provider, final vendor decision still open.** Neither Mapbox's card requirement nor its actual address-search data quality for Sri Lanka could be confirmed with certainty (Mapbox's own published country-coverage table for its Geocoding/Search API does not list Sri Lanka at all — see chat record). Rather than commit further to an unconfirmed vendor, Shashika created a **Stadia Maps** API key (no card required, confirmed) purely to get the map/location-picker function actually running and testable now. **This is explicitly not the final decision** — the eventual production choice remains open between Google Maps and Mapbox, to be settled once there's been a chance to evaluate real address-search quality for Colombo/Sri Lanka against a live map. The frontend implementation (`frontend/meetup-scheduling-PLAN.md`'s testing addendum) is built so this swap is contained: the existing manual-entry stopgap is commented out rather than deleted, and the Stadia-backed widget sits behind the same narrow contract, so replacing it later doesn't mean re-touching the rest of the Schedule flow. One real limit on "just swap the provider," flagged so it isn't discovered late: Stadia Maps (and MapTiler) render via the MapLibre GL Flutter package, while Mapbox and Google Maps each have their own, different, incompatible Flutter SDK. Swapping *within* the MapLibre-compatible group (Stadia ↔ MapTiler) really is close to "just change the API key." Swapping *to* Mapbox or Google later means writing a new widget against a different package — contained to one file by this design, but not a config-only change. Tracked as an active testing shortcut in `TESTING-NOTES.md` and [Testing Notes](../00-project/testing-notes.md) — must not be mistaken for the production decision.

**Third correction (2026-08-18) — the map provider question splits by platform; iOS is now settled, Android stays provisional.** Prompted by Shashika asking whether the phone's own map app could just be used directly. Two distinct needs turned out to have different answers:

- **Viewing a meetup's location** (detail page, "get directions") needs no embedded map or vendor at all — a `url_launcher` deep link out to whichever maps app is already on the device (Apple Maps on iOS, Google Maps on Android) handles this for free, added regardless of the picker decision below.
- **Picking a location** (the Schedule flow's search + pin-drop) can't be delegated the same way — neither Apple Maps nor Google Maps exposes an OS-level "pick a location and return it to the calling app" contract to third-party apps (Android's old Places Picker widget was deprecated and removed years ago; Apple Maps has never had an equivalent). This still needs an embedded map+search.

For the embedded picker specifically: **iOS uses Apple's native MapKit** (`apple_maps_flutter` or an equivalent MapKit-backed package) — free, no API key, no billing account, ships with the OS, settled as the iOS decision rather than provisional. **Android stays on Stadia Maps for now** — confirmed Google's own Maps SDK for Android requires a billing-enabled Cloud project even for its unlimited-free map-display tier (checked directly against Google's docs), so "use the native Android map for free" doesn't actually dodge the card requirement the way MapKit does on iOS. Android's final provider (Stadia vs. Mapbox vs. Google) is still the open question from the second correction above — this correction only settles iOS.

Both platforms' search must behave consistently with each other and with what iOS users already expect from Apple's own Maps app: debounced live suggestions as the user types, tap a suggestion to select it, *or* type a full query and submit directly (search button / return key) without picking a suggestion — either path recenters the map and drops the pin. Same interaction contract on both platforms even though the underlying API differs (MapKit's local search completer on iOS, Stadia's autocomplete/search endpoints on Android), so the feature doesn't feel different depending on which phone someone's using.

We do not attempt to hard-block non-public addresses (no reliable way to distinguish "a stranger's home" from "a legitimate meeting spot" from geocoding data alone). Instead: the location step shows the existing pre-meetup safety copy ("Choose a public place...") from [Safety UX Flows](../05-ux/safety-ux-flows.md), and Search Box results are biased toward POI-category places (cafes, restaurants, offices, transit hubs) over raw street addresses, without forbidding the latter outright.

### 5. Capacity: auto-reject on overflow

A Meetup's `capacity` is a hard cap set at creation. Once accepted requests reach capacity, further pending/new requests are auto-resolved as rejected with a "this meetup is full" reason, rather than queued. Simpler to build and reason about than a waitlist; revisit if popular slots make this a real complaint once there's usage data.

### 6. Notifications: Firebase Cloud Messaging (FCM), distinct from the earlier Firebase-for-OTP decision

Request accepted/rejected, and a new request received, need to reach the relevant user even if the app isn't foregrounded — that's push notification territory, not just an in-app Pub/Sub-driven UI update. FCM is the standard cross-platform (Android native + iOS via APNs bridge) push-delivery pipe, free at this scale, and — importantly — **unrelated to the earlier decision to move phone-OTP delivery off Firebase Phone Auth** ([ADR-012](adr-012-level-2-3-verification-delivery-and-identity-anchors.md)'s correction): that decision was about SMS delivery for one-time codes needing to work identically on iOS, where Firebase Phone Auth is effectively Android-only; FCM push notifications work natively on both platforms and were never part of that tradeoff. Delivery mechanism: the backend's existing Pub/Sub event bus ([ADR-008](adr-008-backend-platform-architecture.md)) publishes `meetup.request.created` / `meetup.request.accepted` / `meetup.request.rejected` events; a small notification-dispatch consumer (new, or folded into an existing worker — Claude Code's call at build time) subscribes and calls the FCM HTTP v1 API. In-app (foreground) delivery can reuse the existing Realtime Gateway/WebSocket path already planned in [System Architecture](../03-architecture/system-architecture.md) instead of a push notification when the user is actively in the app — push is specifically for the backgrounded/closed case.

### 7. The mock Matches tab is retired in favor of this feature, built production-grade

`MatchesPage`/`MockMatchingService`/`MatchProfile` (currently a placeholder swipe-style UI over hardcoded data) are replaced, not kept running in parallel. The Matches tab becomes the real surface for: browsing open Meetups near you filtered by intent, hosting a new one ("Schedule Today" / "Schedule for Later"), and a "My Meetups" view (hosted + requested-to-join, with request management for hosts). This is "production-grade" in the sense that it's wired to a real backend service, not that it includes the eventual AI-driven compatibility matching — that remains genuinely Phase 3, deferred, and would layer in later as a *ranking/suggestion* signal over the same underlying Meetup data, not a rebuild of it.

## Consequences

- **Real behavior change, not additive-only**: existing Level 1a users lose access to what they can currently do in the mock Matches tab (which had no gating at all) the moment this ships, since hosting/requesting now requires Level 2. Acceptable and intended — the mock never had real strangers behind it, so there was no real safety exposure to begin with; this closes that gap before real users are involved.
- **New Mapbox cost surface, likely negligible at pilot scale**: both map loads and Search Box requests are metered per-request beyond their separate monthly free tiers — worth Shashika reviewing Mapbox's current pricing before this goes live more broadly than the invite-only launch ([ADR-005](adr-005-invite-only-company-based-closed-launch.md)), same review discipline as any metered vendor.
- **New backend service**: a Meetup service (own Cloud Run deployment, own Postgres tables, Pub/Sub publisher) per [System Architecture](../03-architecture/system-architecture.md)'s already-anticipated "Meetup/Safety-gate service" component — this ADR is what actually greenlights building it now, rather than it staying a documented-but-unstarted line item.
- **Matching engine is not being designed away** — Phase 3's AI-driven compatibility matching still has a real place in the roadmap, now explicitly reframed as a discovery/ranking layer over Meetup data rather than the mechanism that creates Meetups in the first place.
- Requires updating: [Domain Model](../02-domain/domain-model.md) (Meetup, new Meetup Request entity — done), [Trust Levels](../02-domain/trust-levels.md)/`IntentType.requiredTrustLevel` note (done), [Action Tracker](../00-project/action-tracker.md) (Maps/FCM prerequisites — done), `backend/meetup-scheduling-PLAN.md` and `frontend/meetup-scheduling-PLAN.md` (new, this slice's execution detail).
