# [ADR-015](adr-015-post-meetup-star-ratings.md) — Post-Meetup Star Ratings

## Status

Accepted (2026-08-19), plan authored by Claude Code, reviewed and approved by Shashika/Claude with three refinements folded in before implementation.

**Partially superseded (2026-08-20, [ADR-016](adr-016-meetup-time-windows-and-host-initiated-lifecycle-closing.md))**: this ADR's Decision section said "`completed` stays deliberately unused; this ADR doesn't revive it," reasoning that rating eligibility only needed the per-participant `happened` trigger. That reasoning still holds and is unchanged — but it only ever covered rating eligibility, not the separate, real need for a host to close a meetup and for "My Meetups" to show open vs. history. [ADR-016](adr-016-meetup-time-windows-and-host-initiated-lifecycle-closing.md) revives `completed` for that distinct purpose. The two are explicitly decoupled: closing a meetup does not gate or affect rating eligibility in any way — this ADR's trigger (`meetup_feedback.happened = true`, per participant) is still the only thing that unlocks rating.

## Context

`frontend/lib/features/profile/profile_page.dart`'s stats row has carried a hardcoded `_StatChip(value: '4.9', label: 'RATING')` placeholder since early in the build — a real rating system was always implied but never modeled. [Domain Model](../02-domain/domain-model.md) and [Safety Features Catalog](../03-architecture/safety-features-catalog.md) mention "user ratings" only descriptively, never as a modeled entity, and no prior ADR covers it.

Explicitly modeled on Uber/PickMe: after a meetup, participants rate each other 1-5 stars, and the resulting average becomes a visible trust signal on profiles and on request/browse cards — closing the gap between "what's this person's trust *level*" (a one-time verification state, [Trust Levels](../02-domain/trust-levels.md)) and "how have people who actually met them rated the experience" (an ongoing behavioral signal).

## Decision

- **Trigger, not a new lifecycle state**: rating eligibility hooks off the existing `SubmitMeetupFeedback` call (`happened: true`) rather than reviving `meetups.status`'s unused `completed` enum value. The moment a participant confirms a meetup happened is, for them, the natural "this is closed, rate who I met" point — pairwise, not a single global "meetup closed" flag. `completed` stays deliberately unused; this ADR doesn't revive it.
- **Anonymous to the ratee**: a user sees only their own aggregate (average + count), never which specific person gave which score. Matches the stated Uber/PickMe precedent, reduces retaliation risk between people who met once.
- **Known, accepted limitation of that anonymity model, not silently absent**: in a small meetup (e.g. capacity 2), "anonymous" is trivially reversible — a single rating can only have come from the one other participant. This is the same limitation Uber/PickMe themselves carry with small-party trips; not solved here, written down as a conscious tradeoff rather than an unexamined gap.
- **Gated on confirmed attendance, checked server-side**: `SubmitRating` requires the *rater* to already have a `meetup_feedback` row with `happened = true` for that meetup — never trusted from the client. A rateable participant does not need their own `happened = true` (a no-show is legitimately ratable by someone who did attend and confirm — the rater's confirmation is the trust anchor, not the ratee's).
- **Ratable set**: host + accepted requesters, excluding self — reuses the existing participant concept `ListMeetupRequests` already computes.
- **One rating per (meetup, rater, ratee), immutable**: no edit/re-rate, enforced by a DB unique constraint plus a `CHECK (rater_user_id <> rated_user_id)` for self-rating (defense in depth — the UI never offers self as a rateable option, so this only matters against a malformed direct API call).
- **Aggregate stored as two columns on `users`** (`rating_average`, `rating_count`), recomputed via `AVG()`/`COUNT()` over `meetup_ratings` inside the same transaction as the insert — not an incremental running update. Self-correcting, avoids drift. Verified against Postgres's actual read-committed re-check behavior: concurrent raters of the same person serialize on that user's row lock, and because each write is a full recompute (not read-old-then-increment), the final state is correct regardless of race timing — no incremental-update race condition to worry about.
- **Why `meetup_ratings` persists every individual rating, not just the aggregate**: the two `users` columns are a derived cache, not the source of truth, and the underlying rows earn their keep four ways — (1) the one-rating-per-pair rule can only be enforced by checking whether a row already exists for that exact (meetup, rater, ratee) triple, there's nothing to check against with an aggregate alone; (2) the aggregate is only ever correctable by recomputing from source — a corrupted or drifted average can't be "fixed" without the individual scores behind it; (3) it's the only way to ever investigate a disputed or manipulated rating (which meetup, which rater, when) — an aggregate gives zero forensic capability; (4) it's what any future smarter-than-a-flat-average feature (trend over time, per-intent breakdowns, fraud-pattern detection across a cluster of accounts) would need, and collapsing to an aggregate now would foreclose all of that permanently. Distinct from this session's earlier Redis/data-lifecycle discussion: a rating has ongoing value for the life of the account it's attached to, unlike an OTP code — it doesn't belong in the "clear once used" bucket.
- **No Pub/Sub event**: `services/auth` and `services/meetup` share one literal Postgres database (confirmed via `docker-compose.yml`'s single `DATABASE_URL`), so `services/meetup` updates the aggregate directly in the same transaction — consistent with how it already joins `users` for trust-level display today. No new topic, no new subscriber.
- **Error-code refinement over the original plan**: "not yet eligible to rate" (rater hasn't confirmed attendance) maps to `Forbidden`, not `Conflict` — `Conflict` is reserved for true duplicate-submission attempts. Keeps the two user-actionable situations ("go confirm attendance first" vs. "you already rated this person") distinguishable to the frontend rather than collapsed into one generic error.
- **Self-rating rejection** (DB CHECK violation) maps explicitly to `ErrInvalidInput`.
- Badges derived from `trustLevel` are untouched — ratings are an additive, separate signal, not a replacement for verification state.

## Consequences

- Schema: `users.rating_average`/`rating_count`, new `meetup_ratings` table (migration `0005`). `MeetupResponse`/`MeetupRequestResponse`/`ProfileResponse` gain joined rating fields, same "joined display info" pattern already used for trust level.
- Sybil/manipulation risk is bounded by the existing Level 2 floor already required to host or request a meetup ([ADR-013](adr-013-host-initiated-meetup-scheduling-with-join-requests.md)) — faking ratings requires multiple genuinely-verified accounts, not solved further by this feature and not required to be.
- Frontend: a new read-only `StarRating` display widget and a post-feedback `RatingPrompt` submission widget, wired into the same three places `TrustLevelBadge`/verification badges were just added (browse card, request/hosted-meetup cards, profile stats row) — replaces the long-standing hardcoded `4.9` placeholder.
