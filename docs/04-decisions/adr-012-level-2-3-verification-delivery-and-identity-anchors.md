# [ADR-012](adr-012-level-2-3-verification-delivery-and-identity-anchors.md): Level 2/3 Verification — OTP Delivery Vendor, Corporate Email MVP Scope, Identity Anchors

**Status:** Accepted

## Context

First concrete build of [ADR-006 - Progressive LinkedIn-First Trust Onboarding](adr-006-progressive-linkedin-first-trust-onboarding.md)'s Level 2 (phone OTP, personal email OTP, personal details) and Level 3 (corporate email, MVP-scoped — see Decision below), on top of the now-working Level 1a LinkedIn slice ([ADR-011 - LinkedIn Onboarding Slice Design](adr-011-linkedin-onboarding-slice-design.md)). Three things needed a real decision before any backend code could be written: who actually sends the phone/email OTPs, how much of the documented Level 3 fraud-detection flow ([Verification Model](../02-domain/verification-model.md) § 5) to build now vs. later, and how to resolve the single-identity-anchor gap flagged during the Level 1a review (`linkedin_sub` is currently the *only* way to identify a user — see [Project State](../00-project/project-state.md) § Blocked, "Single identity anchor risk"). Execution detail lives in `backend/PLAN.md` and `frontend/PLAN.md`; this ADR records only what should outlive those files.

## Decision

- ~~**Phone OTP: Firebase Authentication (Phone Auth), not a custom SMS integration.**~~ **Superseded — see Correction (2026-08-17) below.**
- **Personal email OTP: backend-generated, not Firebase.** Firebase Auth's email flows (email-link sign-in, password reset) are tied to creating/managing a Firebase Auth *user* — this app's identity system is its own Postgres-backed `users` table, not Firebase Auth users, so piggybacking Firebase's email flows here would mean maintaining a shadow user object for no reason. Instead: the auth service generates a random 6-digit code, stores only its hash + a short expiry (mirroring the existing refresh-token hash-and-expiry pattern in `refresh_tokens`), and sends it via a lightweight transactional email API call from the Go backend. **Exact provider (SendGrid, Postmark, or equivalent) is not decided in this ADR** — a free-tier transactional email API is a same-day integration whenever it's time to wire the API key, and shouldn't block writing the rest of this slice. Flagged in `backend/PLAN.md` as a human prerequisite step, same treatment as the LinkedIn app registration was for [ADR-011](adr-011-linkedin-onboarding-slice-design.md).
- **Corporate email: MVP-scoped for this pass, not the full [Verification Model](../02-domain/verification-model.md) § 5 flow.** Build only: OTP/link verification of the address, extract `company_domain`, store `company_domain` + `work_email_verified` + `verified_at` (never the raw address, per [ADR-003 - Ephemeral Work Email Verification](adr-003-ephemeral-work-email-verification.md) — unchanged, still binding). **Explicitly deferred**, same "conscious, documented narrowing" treatment [ADR-004 - Defer Dating and Open Ride-Sharing](adr-004-defer-dating-and-open-ride-sharing.md) used: domain-age/SPF/DKIM/DMARC checks, the company verification database, and manual review for unknown domains. Every corporate email accepted by this MVP is trusted on "it verified via OTP + isn't a free-mail domain" alone — free/role-based domain rejection ([Verification Model](../02-domain/verification-model.md) § 5's existing lists) stays in, since it's cheap and already fully specified; the reputation/review machinery is what's cut. Revisit before this trust signal is used for anything Enterprise-tier-load-bearing ([Revenue Model](../01-product/revenue-model.md)).
- **`phone_number` and `personal_email` get their own `UNIQUE` constraints**, resolving the open item flagged during the Level 1a review. This makes them real secondary identity anchors, not just verified profile fields — a user whose LinkedIn account becomes locked, deleted, or revoked still has an account-recovery path that doesn't depend on LinkedIn. Both are nullable (a user can be Level 1a-only, with neither set yet) but non-null values must be unique platform-wide. Re-linking a different LinkedIn account to an existing phone/email-anchored account is **not** designed here — flagged as still open.
- **Personal details (legal name, address) are captured as part of this same slice**, matching the documented Level 2 definition exactly (not narrowed) — per [Verification Model](../02-domain/verification-model.md) § 4, address is stored but never shown to other users, and fuzzed the same way location privacy is handled elsewhere in the app.
- **All of Level 2 and Level 3 is skippable at every step**, surfaced via a short trust/benefit message rather than a hard gate — consistent with the existing design (Level 1a already permits limited discovery; Level 2 is what unlocks full matching, per [Trust Levels](../02-domain/trust-levels.md)). This is enforced the same way `IntentType.requiredTrustLevel`/`isUnlockedFor` already gates intents client-side, backed by the server-authoritative `trust_level` the client only ever displays, never decides with (same principle [ADR-009 - JWT Auth Strategy](adr-009-jwt-auth-strategy.md) established). The identical set of steps (phone, personal email, personal details, corporate email) must be reachable from `ProfilePage` after onboarding, not just during it — a user who skipped shouldn't have to re-onboard to finish later.

## Correction (2026-08-17): phone OTP moved off Firebase, onto the same backend-owned pattern as email

Reconsidered after evaluating actual setup cost, not a factual error like [ADR-011](adr-011-linkedin-onboarding-slice-design.md)'s PKCE correction — Firebase Phone Auth does work correctly on both Android and iOS (a passing concern that it might not was checked and is false; iOS just needs an extra APNs authentication key uploaded for its silent-push app-attestation step, where Android gets the equivalent from Play Integrity automatically). The actual reasons to move off it: it requires upgrading the Firebase project to the Blaze (pay-as-you-go) plan with a live billing account attached — the one Firebase Auth feature not available on the free Spark plan at all, even within a free quota — plus the iOS APNs key setup, for a phone-verification path that would otherwise be the *only* piece of this slice routed through Firebase; personal and corporate email verification were already being built as backend-owned OTP flows (generate a code, hash it, store it with an expiry, send it via a pluggable sender interface — see Decision below). Running two different OTP mechanisms side by side (Firebase-managed for phone, backend-owned for email) for the same conceptual action was more moving parts than the alternative.

**Revised decision**: phone verification uses the identical backend-owned pattern as personal/corporate email. The `verification_codes` table gains a third `purpose` value (`'phone'`); a new `SmsSender` interface (mirroring the already-designed `EmailSender`) sends the code via a plain SMS API instead of Firebase's client SDK.

**SMS provider chosen (2026-08-17): Twilio — specifically the plain Programmable Messaging API, not Twilio Verify.** Twilio Verify was considered and deliberately rejected despite being the most convenient option (handles the OTP lifecycle entirely on Twilio's side) precisely because that would reintroduce a second, separate OTP mechanism for phone — the exact problem this correction exists to undo. Plain Messaging API is just an SMS carrier; this backend keeps owning code generation/hashing/storage/verification for phone exactly as it does for email. Credentials (`TWILIO_ACCOUNT_SID`/`TWILIO_AUTH_TOKEN`/`TWILIO_PHONE_NUMBER`) are human-filled in `backend/.env`, with `LoggingSmsSender` as an automatic fallback when they're empty so local dev/tests aren't blocked on Shashika having a live Twilio account yet.

**Email provider chosen (2026-08-17): Resend.** Modern developer-friendly API, 3,000 free emails/month with no credit card required — a good fit for a pre-revenue, cost-conscious project. Requires a verified domain for the "from" address in production (Resend supplies DNS records to add), but their sandbox address (`onboarding@resend.dev`) works without domain verification for testing, so this isn't blocking. Credentials (`RESEND_API_KEY`/`RESEND_FROM_EMAIL`) are human-filled in `backend/.env`, `LoggingEmailSender` as the automatic fallback when empty — same treatment as Twilio above.

**Consequences of this correction**: no `firebase-admin-go` backend dependency, no Firebase service-account key/secret, no Blaze-plan billing account requirement, no iOS APNs key setup. The Flutter app drops `firebase_core`/`firebase_auth` entirely — phone verification becomes UI-identical to the email verification screens (number entry → shared OTP-entry widget), not a separate Firebase-managed flow. One remaining open item, same as email: an actual SMS provider still needs to be chosen and an API key obtained before this can send a real message — flagged as a human prerequisite, not blocking the rest of the build.

## Consequences

- ~~Firebase Phone Auth means the app now talks to two different backends...~~ / ~~The Go backend gains a new dependency (`firebase-admin-go`)...~~ **Both superseded by the 2026-08-17 correction above** — phone verification now stays entirely on this app's own gateway, same as everything else per [ADR-008](adr-008-backend-platform-architecture.md), with no Firebase dependency at all.
- Corporate email's MVP scope means Level 3 is a materially weaker signal than the fully-specified design until the deferred pieces are built — acceptable because Level 3 is optional and not load-bearing for safety (unlike Level 2, which gates matching with strangers); revisit before making any product promise that leans on Level 3 specifically (search-by-company, Enterprise tier). **Named explicitly (flagged 2026-08-17, [Verification Model](../02-domain/verification-model.md) § 5 carries the full detail)**: this MVP does not stop someone from registering a fresh lookalike domain (e.g. `acme-hr.com` for real company `acme.com`) and passing verification cleanly — the OTP only proves mailbox control, not employer legitimacy. Accepted for MVP because Level 3 doesn't gate safety, but it does mean the "Work Email Verified" badge's UI copy must say what was actually checked (mailbox control) rather than imply something stronger (a legitimate employer) — this is a hard requirement on the frontend addendum's copy, not a nice-to-have.
- Adding `UNIQUE` constraints on `phone_number`/`personal_email` now, while both are still nullable, avoids a much more painful backfill-and-constrain migration later once real user rows exist without them.
- Execution detail (exact RPC signatures, migration SQL, screen-by-screen frontend spec) lives in `backend/PLAN.md`/`frontend/PLAN.md`, not here.
